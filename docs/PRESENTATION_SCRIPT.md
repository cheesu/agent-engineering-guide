### 슬라이드 2 — 전체 워크플로우 한눈에

전체 흐름을 먼저 보여드리겠습니다.

사용자가 "일해라"라고 입력하면, CLAUDE.md라는 파일이 자연어 라우팅 역할을 합니다. 어떤 말을 했는지에 따라 적절한 플로우로 분기시키는 거죠.

그다음은 **메인 오케스트레이터**(Sonnet)가 ADO 조회·확인 게이트·브랜치 생성을 맡고, **Planner(Opus)**가 Serena로 분석해 핸드오프 텍스트를 돌려주면 오케스트레이터가 `.claude/state/handoff.md`에 저장합니다. 이어서 **Implementer(Sonnet)** 서브에이전트가 그 파일을 읽고 구현합니다. 마무리 단계에서는 **Deterministic Preflight** 후 **Reviewer(Opus)**가 `git diff`로 verdict를 내리고, 최종 승인 뒤 `finish_approval` 토큰으로 커밋·푸시·Draft PR까지 진행됩니다.

### 슬라이드 3 — 기술 스택 구성

이 워크플로우는 네 계층으로 구성됩니다.

첫 번째, **오케스트레이션** 계층입니다. Claude Code CLI가 전체를 총괄하고, CLAUDE.md가 자연어를 보고 어떤 플로우를 탈지 결정합니다.

두 번째, **실행 역할** 계층입니다. Planner·Implementer·Reviewer 세 서브에이전트가 Agent 도구로 스폰되고, 모델은 Opus·Sonnet·Opus로 고정됩니다. 메인은 라우팅과 확인 게이트, state 파일 저장을 담당합니다. 자세한 실행 흐름은 두 번째 탭에서 다룹니다.

세 번째, **스킬** 계층입니다. `hqn-ado-pickup-task`·`finish`, 자연어 단축용 `pickup`·`finish`·`tasks`, 그리고 `hqn-frontend-guardrails` 등 마크다운으로 묶인 지시 묶음입니다.

네 번째, **MCP 서버**입니다. Azure DevOps에 직접 붙어서 Work Item이나 PR을 조작하고, Serena라는 MCP로 코드를 심볼 단위로 탐색합니다.

### 슬라이드 4 — CLAUDE.md 자연어 라우팅

CLAUDE.md가 어떻게 라우팅을 하느냐면, 패턴 기반입니다.

"일해라", "픽업", "작업해" 같은 말을 하면 pickup 플로우로 진입하고, "마무리", "끝내", "PR 만들어" 같은 말을 하면 finish 플로우로 진입합니다.

동시에 고정 컨텍스트도 선언해둡니다. ADO 프로젝트는 MWA, 베이스 브랜치는 product/hqn/main, 응답은 한국어. 이 파일을 레포에 체크인하기 때문에 팀원 누가 쓰든 동일한 행동이 보장됩니다. 개인 설정에 의존하지 않는 거죠.

---

### 슬라이드 5 — 역할 분담

실행 역할을 좀 더 자세히 보겠습니다.

**메인 오케스트레이터**는 Sonnet입니다. 사용자와 대화하고 CLAUDE.md·스킬에 따라 플로우를 택한 뒤, 서브에이전트를 스폰하고, planner·reviewer가 반환한 긴 텍스트는 직접 히스토리에 쌓지 않고 `.claude/state/handoff.md` 또는 `review_findings.md`에 저장합니다. planner와 reviewer는 Write가 금지되어 있어서, 파일 기록은 오케스트레이터 책임입니다.

**Planner**는 Opus로, Serena로 코드베이스를 탐색해 핸드오프 텍스트만 반환합니다. Edit·Write 없음.

**Implementer**는 Sonnet 서브에이전트로, `handoff.md`를 읽고 scoped lint·`yarn tsc --noEmit`까지 수행합니다. not ready verdict가 나면 findings를 읽고 수정 루프가 돌 수 있습니다(정책상 재리뷰 제한 등은 스킬에 정의).

**Reviewer**는 Opus로, Preflight 통과 후 `git diff` 중심으로 리뷰해 verdict를 냅니다. Edit·Write 없음.

### 슬라이드 6 — MCP 서버

외부 시스템과의 연결은 MCP 서버가 담당합니다.

**Azure DevOps MCP**는 Work Item 조회, 상태 변경, 브랜치 생성, PR 생성, Work Item과 PR 연결까지 다 합니다. 사람이 ADO 웹 콘솔을 왔다 갔다 할 필요가 없어지는 거죠.

**Serena MCP**는 좀 독특한데, 코드를 파일 단위가 아니라 심볼 단위로 탐색합니다. 예를 들어 CTAMultiViewer.tsx 같은 대형 파일이 있으면 전체를 읽는 게 아니라 필요한 함수나 클래스만 골라서 읽고 수정할 수 있습니다. 이게 나중에 비용 최적화에서 아주 중요한 역할을 합니다.

## TAB 02. 모델 분리 전략

### 슬라이드 1 — 커버

두 번째 탭은 모델 분리 전략입니다.

핵심 아이디어는 간단합니다. 비싼 모델은 생각하는 데 쓰고, 싼 모델은 실행하는 데 씁니다. Opus 4.6과 Sonnet 4.6을 에이전트별로 고정하고, 도구 접근 범위까지 함께 분리하는 설계입니다.

### 슬라이드 2 — 먼저 개념부터 정리

두 번째 탭에 들어가기 전에, 용어부터 한번 맞추고 가겠습니다.

여기서 **메인 Claude**는 사용자와 직접 대화하는 오케스트레이터입니다. **CLAUDE.md와 skill**은 그 오케스트레이터가 읽는 규칙서고요. **서브에이전트**는 메인 Claude가 Agent 도구로 띄운 별도 프로세스입니다.

그리고 "팀 에이전트", "멀티에이전트" 같은 말은 사실 별도 기술이 아니라, 메인 오케스트레이터가 여러 서브에이전트를 운용하는 같은 패턴을 다르게 부르는 표현입니다.

마지막으로 **모델 스플릿**은 이 구조 위에 얹는 최적화 레이어입니다. 즉, 서브에이전트라는 메커니즘이 먼저 있고, 그 위에서 Planner는 Opus, 구현은 Sonnet처럼 역할별 모델을 나누는 거죠.

---

### 슬라이드 3 — 이 프로젝트의 실제 실행 흐름

핵심은 **planner · implementer · reviewer 세 서브에이전트가 모두 Agent 도구로 스폰**된다는 점입니다.

pickup에서 Planner가 핸드오프 텍스트를 반환하면 오케스트레이터가 `handoff.md`에 쓰고, Implementer가 그 파일을 읽어 구현합니다. finish에서는 Preflight 후 Reviewer가 `git diff`로 verdict를 내립니다. not ready면 `review_findings.md`에 저장된 뒤 Implementer를 다시 스폰하는 루프가 문서에 정의되어 있습니다(재리뷰 1회 등).

커밋·푸시·PR은 메인 오케스트레이터가 `finish_approval` 토큰을 전제로 실행합니다.

---

### 슬라이드 4 — 핵심 메커니즘

이게 어떻게 가능하냐면, Claude Code에 Agent 도구라는 게 있습니다.

흐름을 보시면, 먼저 Agent 도구를 호출하면서 어떤 에이전트를 쓸지 지정합니다. 그러면 `.claude/agents/` 폴더에서 해당 에이전트의 마크다운 파일을 찾아 로드합니다. 그 파일 맨 위에 frontmatter라는 설정 영역이 있는데, 거기에 `model: claude-opus-4-6` 이렇게 적혀 있으면 그 모델로 독립 프로세스가 뜹니다.

핵심은 메인 프로세스와 **완전히 분리된 컨텍스트**에서 실행된다는 겁니다. 다른 모델, 다른 컨텍스트, 제한된 도구.

---

### 슬라이드 5 — 에이전트 정의 파일 예시

실제 파일이 어떻게 생겼는지 보시면, 별거 없습니다.

【코드 세 개를 차례로 가리키며】

Planner는 `model: claude-opus-4-6`, tools에 Read, Glob, Grep, Bash, WebFetch. 읽기 전용 도구만 있죠. Implementer는 `model: claude-sonnet-4-6`, tools에 Edit, Write가 추가됩니다. Reviewer는 다시 Opus인데 tools가 가장 적습니다. Read, Glob, Grep, Bash만.

마크다운 frontmatter 몇 줄이 모델과 도구 제한을 동시에 결정하는 겁니다.

---

### 슬라이드 6 — 모델 결정 우선순위

그런데 모델을 결정하는 경로가 여러 개 있을 수 있습니다. 우선순위가 있어요.

가장 높은 건 Agent 도구를 호출할 때 직접 model 파라미터를 넘기는 겁니다. 두 번째가 지금 저희가 쓰는 방식인 에이전트 파일의 frontmatter입니다. 세 번째는 프로젝트 settings.json, 네 번째는 회사 원격 정책, 다섯 번째가 Claude Code 기본값인 Sonnet입니다.

저희는 2번, frontmatter에 모델을 고정하는 방식을 씁니다. 이렇게 하면 팀원 누가 실행하든 항상 같은 모델이 배정됩니다.

서브에이전트의 모델은 각 `agents/*.md` frontmatter가 고정하며, 메인의 `remote-settings.json` 기본값과 독립입니다.

---

### 슬라이드 7 — 도구 접근 범위 분리

모델만 나누는 게 아니라 도구 접근도 함께 나눕니다. 이 부분이 중요합니다.

표를 보시면, Planner에는 Edit/Write가 없고, Implementer에는 WebFetch/WebSearch가 없고, Reviewer에도 Edit/Write가 없습니다.

왜 이렇게 하냐면, "이 에이전트는 파일을 수정하지 않을 거야"라고 지시문에 적는 건 모델의 판단을 믿는 겁니다. 하지만 도구 자체를 제거하면 판단과 무관하게 물리적으로 불가능해집니다. 신뢰가 아니라 구조로 막는 거죠.

---

### 슬라이드 8 — 파일 릴레이로 얻는 것 · 감수하는 것

현재 구조는 **state 파일로 에이전트 간 데이터를 넘기는 방식**입니다.

이득은 토큰입니다. planner가 반환한 긴 핸드오프를 메인 대화에 반복해서 붙이지 않고 `handoff.md` 한 곳에만 두면, 메인 컨텍스트 팽창을 억제할 수 있습니다. reviewer도 마찬가지로 findings를 파일로 넘깁니다.

감수하는 점은 **핸드오프 품질이 성패를 가른다**는 겁니다. implementer는 대화 맥락 없이 `handoff.md` 중심으로 움직이므로, 계획이 빈약하면 구현이 빗나갈 수 있습니다. `git diff` 중심 리뷰는 Read 비용을 줄이지만 diff만으로는 의도 맥락이 부족할 수 있습니다.

추가로 **Preflight**로 브랜치명·금지 경로·tsc·lint를 리뷰어 스폰 전에 검사해, 실패 시 Opus를 불필요하게 켜지 않도록 했습니다.

---

### 슬라이드 9 — 가성비의 근거

그래서 실제 비용 절감 효과가 어떻게 나오느냐.

토큰 볼륨이 에이전트별로 매우 비대칭입니다. Planner는 ADO 정보 읽고 심볼 탐색하고 핸드오프 문서 쓰는 게 끝입니다. 태스크당 1회. Reviewer도 마찬가지로 변경 파일 보고 리뷰 의견 내는 게 끝, 태스크당 1회.

반면 **Implementer(Sonnet)** 구간은 파일을 읽고, 수정하고, lint·tsc를 돌리고 반복합니다. 토큰 소비가 가장 큰 구간입니다.

결과적으로 고볼륨 구현은 Sonnet 서브에이전트로, 저볼륨 계획·리뷰는 Opus로 갑니다.

---

### 슬라이드 10 — Serena MCP와의 상승효과

여기서 Serena MCP가 결정적인 역할을 합니다.

Serena가 없으면 Planner(Opus)가 코드를 분석하려면 파일 전체를 읽어야 합니다. 수천 줄짜리 파일을 통째로 읽으면 Opus 토큰이 폭증하니까, 모델 분리로 얻은 비용 이득이 상쇄됩니다.

Serena가 있으면 필요한 심볼만 타겟해서 읽으니까, Planner의 토큰 소비가 최소화됩니다. 모델 분리와 Serena가 결합돼야 비용 최적화가 완성되는 구조입니다.

---

### 슬라이드 11 — 언제 이득이고 언제 손해인가

솔직한 평가를 하면, 항상 싸지는 건 아닙니다.

효과가 큰 경우는 파일 탐색과 코드 작성이 많은 중~복잡 태스크, Serena가 잘 동작하는 환경, Planner가 한 번에 깔끔한 핸드오프를 만들어내는 경우입니다.

반대로 손해인 경우는, 텍스트 한 줄 고치는 단순 태스크에 Planner-구현-Reviewer 풀 플로우를 도는 건 오버헤드입니다. 또 핸드오프가 실패해서 Planner가 재시도를 반복하면 Opus 비용이 누적되고요.

정리하면, 모든 작업에 이 플로우를 강제하는 건 아니고 작업의 복잡도에 따라 판단해서 쓰는 게 맞습니다.

### 슬라이드 12 — 설정 최소 요구사항

이 구조를 도입하려면 뭐가 필요하냐, 사실 많지 않습니다.

필수는 `.claude/agents/` 아래 에이전트 마크다운 파일에 model 필드를 넣는 것, 그리고 CLAUDE.md나 스킬에서 이 에이전트를 호출하도록 지시하는 것. 이 두 가지만 있으면 됩니다.

Claude Code 기본 기능이라서 외부 라이브러리나 별도 인프라는 필요 없습니다.

## TAB 03. 하네스 엔지니어링

### 슬라이드 1 — 커버

세 번째 탭, 하네스 엔지니어링입니다.

지금까지 도구 접근 제한이나 CLAUDE.md 지시 같은 걸 봤는데, 이것만으로는 부족합니다. Claude가 CLAUDE.md 지시를 잊거나, 의도치 않게 위험한 행동을 할 수 있거든요.

하네스는 Claude의 "의지"와 무관하게 물리적으로 막는 레이어와, 지키도록 유도하는 레이어를 함께 쓰는 설계입니다.

---

### 슬라이드 2 — 6개 레이어 한눈에

총 여섯 개 레이어로 구성됩니다.

L1·L2는 PreToolUse 훅입니다. L1은 경로 보호, L2는 Bash용 셸 게이트로 파괴적 git·브랜치 생성·ADO CLI 등을 검증합니다.

**L3는 MCP ADO 전용 PreToolUse**입니다. `hqn_guard_mcp_ado.py`가 `wit_update_work_item`, `repo_create_branch`, `repo_create_pull_request` 같은 MCP 호출에도 start/finish 승인 토큰을 요구합니다. 예전에 Bash 훅만 있을 때 생기던 검증 공백을 메운 레이어입니다.

L4는 PostToolUse로, HQN 경로 편집 후 검증 리마인더를 주입합니다. `.edit_context_injected` 플래그로 **세션당 한 번만** 주입됩니다.

L5는 승인 토큰 JSON, L6은 Skill·CLAUDE.md 소프트 규칙입니다.

---

### 슬라이드 3 — 파일 구조

실제 파일 구조를 보시면, 전부 `.claude/` 디렉토리 안에 있습니다.

settings.local.json이 훅 배선과 권한을 설정하고, agents·skills·hooks/scripts에 각각 정의와 `hqn_guard_mcp_ado.py` 등이 있습니다. state에는 승인 토큰뿐 아니라 `handoff.md`, `review_findings.md`, 복잡도 판정 파일, PostToolUse 세션 플래그도 둡니다.

참고로 훅 스크립트를 Python으로 작성한 이유는, json 파싱, 절대경로 resolve, 정규식, 시간 비교 같은 작업이 Python 표준 라이브러리와 딱 맞아떨어지기 때문입니다. 다만 매 도구 호출마다 Python 프로세스를 fork하니까 누적 지연이 있는 건 트레이드오프입니다.

---

### 슬라이드 4 — L1 경로 보호

L1부터 하나씩 보겠습니다.

Edit이나 Write 도구가 호출되면 hqn_protect_paths.py가 먼저 실행됩니다. 대상 파일의 절대경로가 `src/pages` 또는 `src/shared` 아래에 있으면, 즉시 deny를 반환하고 도구 실행이 취소됩니다.

왜 이 두 경로를 막냐면, src/pages는 Next.js Pages Router라 HQN 작업이 건드리면 다른 제품 라우팅에 영향을 줍니다. src/shared는 전사 공유 컴포넌트인데, HQN이 단독으로 바꾸면 다른 팀에 회귀 위험이 생깁니다.

절대경로로 resolve해서 비교하기 때문에 심볼릭 링크나 `../` 같은 우회도 차단됩니다.

---

### 슬라이드 5 — L2 셸 명령 게이트

L2가 하네스의 핵심입니다. Bash 도구가 호출될 때마다 4단계 검사를 순서대로 실행합니다.

첫 번째, `git reset --hard`, `git push --force` 같은 파괴적 git 명령을 정규식으로 잡아서 즉시 차단합니다.

두 번째, 브랜치 생성 명령이면 브랜치명 패턴이 맞는지, compound command가 아닌지, 현재 브랜치가 main인지, 워킹트리가 깨끗한지, HEAD가 origin과 일치하는지, start_approval 토큰이 유효한지, 이 여섯 가지를 전부 확인합니다.

세 번째, ADO 상태를 변경하려는 명령이면 start_approval 토큰의 Work Item 번호와 일치하는지 검증합니다.

네 번째, 커밋이나 푸시 명령이면 finish_approval 토큰이 유효한지, 로컬 전용 파일이 staged에 섞여 있지 않은지, PR은 반드시 Draft로 만드는지 확인합니다.

---

### 슬라이드 6 — L4 컨텍스트 주입

L4는 앞의 하드 레이어들과 달리 차단이 아니라 정보를 주입합니다.

Edit이나 Write가 완료된 직후에, 대상이 HQN 경로나 locales 경로에 해당하면 PostToolUse 훅이 실행됩니다. 이미 `.edit_context_injected` 플래그가 있으면 같은 세션에서는 건너뜁니다. 플래그는 pickup 시작 시 지워져 새 작업마다 다시 한 번 주입됩니다.

Claude가 "다 했습니다"를 성급하게 선언하지 않도록 리마인더를 끼워 넣는 겁니다.

---

### 슬라이드 7 — L5 승인 토큰 시스템

승인 토큰은 이 하네스의 핵심 아이디어 중 하나입니다.

보통 Claude에게 "이거 해도 되냐"고 물어보면, Claude가 판단해서 "네"라고 대답한 걸 다시 Claude가 기억하는 구조잖아요. 문제는 Claude가 잘못 기억하거나 착각할 수 있다는 겁니다.

그래서 사용자가 "네"라고 할 때 실제로 JSON 파일을 생성합니다. 이 파일에 어떤 레포에서, 어떤 Work Item에 대해, 언제 승인했고, 언제 만료되는지가 기록됩니다.

나중에 브랜치를 만들거나 커밋을 하려면 훅이 이 파일을 읽어서 유효한지 검증합니다. Claude의 추론과 완전히 독립적인 거죠.

시작 토큰은 TTL 1시간, 완료 토큰은 TTL 2시간입니다. 구현에 시간이 더 걸리니까 완료 쪽을 길게 잡았습니다.

---

### 슬라이드 8 — 훅 vs Skill 역할 분담

이렇게 규칙이 많으면 어디에 넣을지 기준이 필요합니다. 원칙은 간단합니다.

**되돌릴 수 없거나 회귀 위험이 큰 건 훅으로 강제합니다.** 경로 보호, 파괴적 git 차단, 브랜치·ADO Bash 검증, **MCP ADO 도구에 대한 동일한 토큰 검증**, Draft PR 강제 같은 것들이죠. 코드로 막으니까 Claude가 어떤 판단을 하든 뚫리지 않습니다.

**형식이나 스타일처럼 틀려도 작업이 유효한 건 스킬로 유도합니다.** 커밋 메시지 형식, 이모지 컨벤션, Serena 우선 사용, 응답 언어 같은 것들입니다. 이건 안 지켜도 코드 자체가 깨지진 않으니까요.

이 구분이 모호하면 하네스가 금방 복잡해지니까, 기준을 명확히 세워두는 게 중요합니다.

---

### 슬라이드 9 — 동작 시퀀스

구체적으로 브랜치 생성 한 번이 어떤 과정을 거치는지 보시면, 왜 이 구조가 단단한지 느낌이 옵니다.

`git checkout -b product/hqn/feature/68900` 명령이 실행되려고 하면, guard_shell 훅이 6개 조건을 순서대로 검사합니다. 브랜치명 패턴, compound command 여부, 현재 브랜치, 워킹트리 상태, HEAD 일치, 승인 토큰 유효성.

하나라도 실패하면 즉시 deny입니다. 특히 compound command 차단이 중요한데, `git checkout -b ... && git push` 같은 식으로 검증을 건너뛰고 이어서 실행하는 경로 자체를 봉쇄합니다.

---

### 슬라이드 10 — 장점

이 구조의 장점을 정리하면,

가장 중요한 건 Claude의 의지와 무관하다는 겁니다. 컨텍스트가 길어져서 앞의 지시를 잊어도, 훅은 매 도구 호출마다 독립적으로 실행됩니다.

에이전트가 세 개든 다섯 개든, 어떤 에이전트가 호출하든 같은 훅이 적용됩니다. 승인은 Claude의 기억이 아니라 JSON 파일 상태로 증명되고, 복합 명령으로 검증을 우회하는 것도 불가능합니다.

---

### 슬라이드 11 — 단점 / 한계

하지만 솔직히 한계도 있습니다. 이미 파악하고 있는 부분이고 순차적으로 개선해 나갈 예정인데, 현재 상태를 공유드리겠습니다.

가장 큰 건 경로가 하드코딩되어 있다는 겁니다. 스크립트에 절대경로가 박혀 있어서, 다른 환경이나 다른 클론 경로에서 조용히 무력화될 수 있습니다.

또 훅이 예외로 실패하면 return 0, 즉 허용으로 처리됩니다. 이른바 Fail-Open 구조인데, 경비원이 기절하면 문이 열리는 셈이에요. 깨진 훅을 인지하지 못할 수 있습니다. 이 부분은 모든 훅 스크립트를 try/except로 감싸서 예외 발생 시 deny를 반환하는 Fail-Closed 구조로 전환하고, 에러 로깅도 추가할 계획입니다.

Python 프로세스를 매번 fork하니까 누적 지연도 있고, TTL이 고정값이라 복잡한 태스크에는 부족하고 단순 태스크에는 과한 경우가 있습니다. TTL은 토큰 발급 시 사용자가 선택하거나 태스크 복잡도에 따라 동적으로 조정하는 방향을 검토 중입니다.

MCP로 ADO를 조작하는 경로는 **`hqn_guard_mcp_ado.py`**로 막았고, 에이전트 정의에도 민감한 ADO MCP 도구를 `disallowedTools`로 빼 두어 서브에이전트가 직접 호출하지 못하게 했습니다. 여전히 배선 누락이나 훅 예외 시 Fail-Open 동작 같은 운영 리스크는 남습니다.

정리하면 한계를 인식하고 있고, 훅은 보조 안전망이지 설계 품질 자체를 대체하는 건 아닙니다.

---

### 슬라이드 12 — 마무리

마지막으로 세 번째 탭을 정리하면, 경로·셸·MCP·PostToolUse·토큰·스킬 여섯 계층이 역할을 나눠 맞물립니다. Claude의 "의지"가 아니라 상태와 검증으로 안전성이 증명되는 구조입니다.

다만 항상 기억해야 할 건, 훅은 보조망이지 설계 품질을 대체하지 않는다는 점입니다. 좋은 에이전트 설계가 먼저이고, 하네스는 그 위에 안전망을 거는 겁니다.
